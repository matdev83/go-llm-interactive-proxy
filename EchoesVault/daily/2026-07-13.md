## Session — 2026-07-13T11:00:00.000Z

Fixed the high-severity Bugbot finding on the Codex app-server verbosity restart: `subprocessBackend.Open` killed an in-use child when a peer turn requested a different process-scoped config, corrupting the in-flight stream.

### Root cause

The Go port dropped Python's per-runtime `request_lock`, which serializes turns on one subprocess for the full stream. Without it, the config-change `KillRuntime` in `Open` (and the internal kill in `EnsureProcess`) could fire while another turn was still streaming on the same stdio transport.

### Changes

- `internal/plugins/backends/acp/runtime_pool.go`: added `SubprocessRuntime.IsInUse()` accessor and `RuntimePool.ClaimForTurn(key, wantConfig)`. `ClaimForTurn` atomically (under `rt.mu`) refuses a runtime another turn still holds (`busy=true`, no claim), and on a successful claim cancels the stale-kill timer and, when the live child was spawned with a different `ProcessConfig`, kills it and resets transcript state. Because the claim is atomic, no peer can begin streaming between the in-use check and the kill, so the reset only runs on the idle path — closing the use-after-kill race for both the `Open` reset and the `EnsureProcess` internal kill.
- `internal/plugins/backends/acp/subprocess_spec.go`: `Open` now calls `ClaimForTurn` instead of `MarkInUse` + the unconditional config-change `KillRuntime`. A busy claim fails explicitly with a "turn is in flight" error instead of killing the peer. `MarkInUse` is retained for tests/direct use; the in-use lifecycle (set by claim, cleared by `Release` on stream close and `Open` error paths) is unchanged. ACP-session protocols (empty `ProcessConfig`) never restart on a claim.
- `EchoesVault/pages/codex-app-server-backend.md`: documented the turn-serialization / in-flight guard behavior.

### Behavior change

A second turn on the same `RuntimeKey` while the first is still streaming is now rejected explicitly instead of corrupting the shared transport. Sequential turns (after the first stream closes) are unaffected, matching the one-turn-at-a-time model a single stdio subprocess requires.
