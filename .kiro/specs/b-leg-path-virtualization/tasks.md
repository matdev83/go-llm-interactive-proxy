- Task 1.1: `internal/core/runtime/tool_call_mandatory_buffering_red_test.go` fails intentionally until Task 7.2 lands; coarse gates run before then will report this failure.
- Task 1.2: `orderingFinalizerProjectRoot` reaches the authoritative root via a reflection probe on `toolcall.Meta` field names `Workspace`/`ProjectRoot`; Tasks 6.1/8.2 must replace it with direct `meta.Workspace.ProjectRoot` access rather than relaxing the assertions.
- Task 1.2: the tool policy observer plane already receives the authoritative workspace view via `applyToolPolicies` (`response_pipeline_observations.go`); only the finalization metadata plane is blind, so no policy-plane change is needed for 5.1.
- Task 1.2: the test-local stand-in finalizer pairs `ActionRewrite` with `ReasonValidPassThrough`; Task 8.1's real finalizer should use a semantically correct reason code.
- Task 1.3: the backend-bound two-pass ordering (attempt transform -> candidate eligibility -> request-part hook -> conversation-view reassertion -> PTB -> `Backend.Open`) already holds in the current runtime, so the delivered `path_virtualization_two_pass_ordering_characterization_test.go` is an intentionally GREEN permanent regression guard, not a pending RED condition. A first review round rejected an earlier RED attempt whose failures came only from anchoring a conversation-view overlay on the very message the rewriter mutates.
- Task 1.3: conversation-view anchor identity is content-derived (`conversationprojection.MessageIdentityOf` hashes message content), so once this feature virtualizes a path-bearing tool-call message, a client steering overlay anchored on that message's pre-virtualization identity can no longer resolve and the executor denies the turn pre-backend (`ErrAnchorMissing` -> `AnchorFailClosed` -> `CommandPreBackendDenial`). This is a real functional gap, but it belongs to conversation-view anchor semantics which `design.md` "Out of Boundary" excludes and no task in 1.1-12.2 owns. Raise it as a separate spec item (suggested as a Requirement 6 continuity sidecar of Task 5.2); do not work around it inside this spec.
- Task 7.1 DONE — `pkg/lipsdk/toolcall/buffering.go` adds the optional capability, matching design.md §6 name-for-name and value-for-value: `BufferingRequirement{ToolCallBufferingRequirement() BufferingSpec}`, `BufferingSpec{MaxArgsBytes int; Overflow OverflowPolicy}`, `OverflowPassThrough = "pass_through"`, `OverflowReject = "reject"`. `toolcall.Finalizer` is BYTE-UNCHANGED (still exactly `{ID, Order, Finalize}`); the capability is satisfied by type assertion only.
- Task 7.1 (reviewer-ruled): NO NEW PLANE WAS NEEDED. design.md §6 conditions a plane on "if the current scalar plane cannot express this independently". `newToolCallAssembler` (`executor_open_attempt.go:994`) already holds the concrete `[]toolcall.Finalizer` slice at construction, so a type assertion there reaches every declaration with zero plane/combiner/registry change.
- Task 7.1: exported constants `DefaultMandatoryMaxArgsBytes` (1 MiB), `MinMandatoryMaxArgsBytes` (64 KiB), `MaxMandatoryMaxArgsBytes` (= `lipapi.MaxEventDeltaBytes` = 8 MiB). Reviewer-ruled correct: design.md names these as contract values consumed by three independent parties (feature config validation, assembler effective-bound computation, config diagnostics); exporting them prevents re-derivation, and it adds NO new dependency edge.
- Task 7.1: `MinMandatoryMaxArgsBytes` (64 KiB) COINCIDENTALLY equals core's `defaultToolCallFinalizationMaxArgsBytes`, and the two are DELIBERATELY NOT COUPLED. Reviewer-ruled correct: design.md fixes 64 KiB and core fixes its own default independently, so coupling them would create a false invariant. Both sides are separately pinned by their own tests. Do not "fix" this by coupling them.
- **Task 7.2 MANDATORY OBLIGATION (reviewer-ruled, SECURITY-RELEVANT):** `DeclaresMandatoryBound()` returns false for a MALFORMED declaration (out-of-range bound, unknown policy, policy without a bound). Nothing in production reads the capability yet, so no bypass is reachable today — but **Task 7.2 MUST branch on the type assertion itself**, not solely on `DeclaresMandatoryBound()`, and when the assertion SUCCEEDS while `Validate() != nil` it must REJECT the affected tool call CLOSED rather than degrade to legacy pass-through. Silently treating a present-but-malformed mandatory declaration as "did not opt in" would downgrade a mandatory completeness requirement into optional handling — the one direction requirements 4.5/4.6/8.3 forbid. This rule is now stated in the `DeclaresMandatoryBound()` doc comment.
- Task 7.1: `Validate()` REJECTS a declared bound below 64 KiB. Reviewer-ruled not a spec violation (design.md §6 pins the configurable range as `[64 KiB, MaxEventDeltaBytes]`, and requirement 7.5 must fail generation compilation on an unsupported bound). Note the accepted trade-off: a future finalizer wanting "fail closed above 8 KiB while the shared cap is 1 MiB" would be refused.
